# Lumi V4 M3 Tool Contract

M3 introduces bounded agent tasks and a policy-gated tool runtime. Tool calls are never executed directly from raw LLM text.

## Execution path

```text
goal
 ↓
LLMTaskPlanner
 ↓ strict PlannerDecision JSON
ToolRegistry lookup
 ↓
PolicyEngine
 ├─ low/read-only → execute
 ├─ high/side-effect → await explicit approval
 └─ critical → deny
 ↓
validated Pydantic arguments
 ↓
per-tool timeout
 ↓
executor
 ↓
durable tool_calls audit row
 ↓
observation returned to planner as untrusted data
```

## M3 tools

| Tool | Risk | Side effect | Approval |
| --- | --- | --- | --- |
| `workspace.list_files` | low | no | automatic |
| `workspace.read_text` | low | no | automatic |
| `workspace.search_text` | low | no | automatic |
| `knowledge.search` | low | no | automatic |
| `workspace.write_text` | high | yes | required |

There is intentionally no shell tool, delete tool, unrestricted filesystem tool, or arbitrary HTTP executor in M3.

## Workspace sandbox

The default root is `.lumi-data/workspace`. Set `LUMI_TOOL_WORKSPACE` to choose another dedicated directory.

Every workspace path must be relative. The runtime resolves symlinks and rejects a result that is not the workspace root or one of its descendants. Text reads are capped by `LUMI_TOOL_MAX_READ_BYTES` and each tool has its own wall-clock timeout.

## Approval contract

A side-effecting proposal is persisted with status `awaiting_approval`. The macOS client displays:

- tool name;
- risk level;
- exact serialized arguments;
- policy/planner reason.

Only `/v1/tool-calls/{id}/approve` can move an awaiting call into execution. `/deny` records the denial and returns it as an observation so the planner may finish or choose a safe alternative. Approval is bound to the already persisted call arguments; the planner does not get to alter them after approval.

## Task budgets

Each task persists:

- `max_steps`;
- `max_tool_calls`;
- `deadline_at`;
- current `step_count`;
- `waiting_tool_call_id`;
- final result/error.

Budget exhaustion terminates the task without executing another tool.

## Auditability

Every proposal is stored in `tool_calls` with arguments, risk, policy reason, status, result/error, and start/finish timestamps. Tool results are fed back into planning only as untrusted observations.

## Known M3 limits

- Planning uses strict JSON generated by the configured chat model; a malformed or unavailable planner fails closed.
- Task transport is request/response rather than task-event streaming.
- The workspace write tool is intentionally narrow and supports text only.
- No capability grants by directory/file exist yet; the entire configured workspace is one trust zone.
- Real-world adversarial prompt-injection evaluation is still required before enabling broader connectors or system tools.
